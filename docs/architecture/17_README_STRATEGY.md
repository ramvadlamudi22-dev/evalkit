# 17 — README_STRATEGY.md

## Audience priority

1. A skeptical senior engineer scanning in 30 seconds.
2. A recruiter (often non-technical) deciding to forward your profile.
3. A first-time user installing the tool.

The README must satisfy all three without becoming three documents. Short, evidence-dense, no fluff.

## Structure (in order)

1. **Header** — name, one-line description, badges (CI, coverage, PyPI version, image size, license).
2. **Hero block (3–5 lines)** — what it does, who it's for, why it exists. No marketing language.
3. **Demo screenshot** — single image of `evalkit run` output (terminal). Real, captured by `make demo`.
4. **Quickstart** — six commands, copy-paste ready, that produce a green run.
5. **Features** — bulleted list, ≤8 items, each linking to docs section.
6. **Architecture** — embedded diagram (`docs/images/architecture.svg`) + 4 sentences.
7. **Sample report** — collapsed `<details>` block with the actual markdown report from `make demo`.
8. **CI integration** — 12-line GitHub Actions snippet a user can paste.
9. **Configuration** — link to suite YAML reference.
10. **Observability** — Jaeger screenshot from `make demo`, with caption naming the spans.
11. **Benchmarks** — generated table (see `METRICS_BENCHMARK_STRATEGY.md`).
12. **Project status & roadmap** — short. Honest. No "v2 will have X, Y, Z" filler.
13. **Comparison** — small prose section, no fake comparison table. Names other tools and what we do differently. Two paragraphs max.
14. **Contributing** — link.
15. **License** — Apache 2.0.

Word budget for the README: under 1,200 words. Anything longer goes to `docs/`.

## Badges

Real badges only:

- CI status (GitHub Actions).
- Coverage (Codecov or shields-from-CI artifact).
- PyPI version.
- Docker image size (from a generated badge).
- License.

We do **not** include:
- "Built with AI" badges.
- "100+ stars" social proof badges that auto-update with vanity metrics.
- Vague "Awesome" badges.

## Screenshots

- All under `docs/images/`.
- Each has a sibling `.json` metadata file with `produced_at`, `command`, `evalkit_version`. Generated by `scripts/demo.sh`.
- Filenames are content-derived (`run-output-{commit_short}.png`), so renames flag accidental drift.
- A CI check verifies that referenced screenshots exist and that their metadata matches the current evalkit version on the release branch.

## Architecture diagram

- Authored as Mermaid in a single `.mmd` file under `docs/architecture/`.
- Rendered to SVG by a script. Both source and SVG are committed.
- Diagram nodes are named after the actual modules in `src/evalkit/` — a reviewer can map each box to a directory. This is the strongest defense against "fake architecture theater."

## Comparison section — discipline

- Name 2-3 real alternatives (e.g., promptfoo, openai/evals, deepeval).
- One sentence on each: what they do well, what we do differently.
- No "X is bad, EvalKit is good" framing.
- No fabricated table of feature checkmarks.

## Roadmap

- Two columns: "Now" (Phase X), "Next" (Phase Y).
- No "someday" column.
- Items removed when deprecated. Stale roadmaps are smell.

## What goes in `docs/` instead of README

- Full suite YAML reference.
- Full evaluator reference.
- Provider-specific setup (OpenAI, Anthropic, Ollama).
- ADRs (Architecture Decision Records) for non-obvious choices.
- FAQ.
- The full planning set lives under `docs/architecture/` (this file and its siblings).

## Anti-smell checklist for the README

Before tagging any release, verify:

- [ ] No "✨" / "🚀" / "🎉" emoji clusters.
- [ ] No paragraphs starting with "Welcome to…" or "In today's fast-paced…".
- [ ] No "Made with ❤️ by…" footer.
- [ ] No screenshots that are clearly mocked / Photoshopped / Figma exports.
- [ ] No claims of "production ready" without the supporting evidence (CI, coverage, image scan).
- [ ] No "TODO:" markers anywhere in `README.md`.
- [ ] No reference to features not yet implemented.
- [ ] Every command in Quickstart has been executed verbatim by `make readme-verify`.
